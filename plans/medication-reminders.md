## خطة التنفيذ

1. **تثبيت قرارات النطاق قبل الكود**
   - اعتماد حالة Dose الناتجة عن زر «تخطي» باستخدام المصطلحات المعتمدة.
   - تحديد نصوص Alarm العامة وغير العلاجية.
   - تحديد Usage Statistics وموافقة المريض عليها.
   - تأجيل Backend إلى أن يحدد صاحب المشروع Firebase أو Supabase.
   - تأكيد سلوك المنطقة الزمنية وتغيير ساعة الجهاز.

2. **إعادة تنظيم أساس Flutter**
   - استبدال شاشة Counter في `lib/main.dart` بهيكل التطبيق الحقيقي.
   - إنشاء طبقات منفصلة لـ `lib/domain` و`lib/core` و`lib/features` و`lib/scheduling` و`lib/data`.
   - إبقاء منطق الجرعات والتذكيرات مستقلًا عن Flutter والـ plugins.

3. **بناء نماذج وقواعد domain النقية**
   - تعريف Medication وReminder وDose وDose Status باستخدام مصطلحات glossary.
   - بناء توليد Doses من Reminder Time وActive Days.
   - بناء انتقالات الحالة: Pending إلى Taken أو Snoozed أو Missed وفق القرارات المعتمدة.
   - جعل Taken idempotent.
   - تعريف ثوابت مسماة لفاصل 10 دقائق وسلوك التكرار بدل الأرقام المضمنة.

4. **إضافة اختبارات domain**
   - اختبار توليد الجرعات والتواريخ.
   - اختبار Taken وSnoozed وMissed.
   - اختبار حدود 10 دقائق، منتصف الليل، جرعتين في الدقيقة نفسها، والنقر المزدوج على Taken.
   - استخدام وقت قابل للحقن بدل وقت الجهاز الحقيقي.

5. **تطبيق واجهة التصميم الأساسية**
   - بناء Theme مطابق لألوان التصميم: الخلفية الفاتحة، السطح الأبيض، الأزرق البترولي، واللون المميز للأفعال.
   - إضافة دعم العربية RTL والإنجليزية LTR عبر ARB files.
   - بناء الشاشة الرئيسية، شريط الأيام، تقدم اليوم، خط الجرعات، التنقل السفلي، وزر إضافة.
   - بناء شاشة Alarm وشاشة تسجيل Taken المطابقة للتصميم المرفق.
   - إضافة حالات التحميل، الفراغ، عدم الاتصال، والرسائل العامة غير العلاجية.

6. **اختبارات الواجهة**
   - اختبار ظهور أزرار Alarm.
   - اختبار الانتقال إلى شاشة تسجيل Taken وظهور الجرعة القادمة.
   - اختبار التبديل بين RTL وLTR.
   - اختبار النصوص العربية والإنجليزية الطويلة والمختلطة.
   - استبدال اختبار Counter الحالي باختبارات السلوك الفعلي.

7. **اختيار Local Store وتنفيذه**
   - طلب موافقة صريحة على `drift` أو `sqflite` قبل إضافة dependency أو schema.
   - حفظ Medication وReminder وDose وAdherence Log محليًا.
   - ضمان أن تسجيل Dose لا يعتمد على الإنترنت.
   - إضافة اختبارات repository والمهاجرات إذا لزم schema.

8. **بناء واجهة Alarm خلف abstraction**
   - طلب الموافقة على حزمة Local Notification/Alarm قبل إضافتها.
   - تعريف interface قابلة للاختبار لجدولة Alarm وإلغائه واستبداله.
   - ربط Taken وSnoozed وMissed بإلغاء أو إعادة جدولة Alarm.
   - منع Alarm قديم من العمل بعد تعديل أو حذف Reminder.

9. **إضافة نقاط إعادة الجدولة والصلاحيات**
   - تغطية تشغيل التطبيق، إعادة تشغيل الجهاز، تحديث التطبيق، تعديل Reminder، حذف Reminder، وتغير الوقت/المنطقة الزمنية.
   - إضافة فحص صحة الصلاحيات مع تحذير ظاهر عند الرفض، دون طلب متكرر إذا بقيت الصلاحية مفعلة.
   - طلب موافقة مسبقة على Android Manifest والصلاحيات exact Alarm وLocal Notification وأي صلاحيات إضافية.

10. **إحصاءات الاستخدام والمزامنة الاختيارية**
    - تنفيذ Local Store كالمصدر الوحيد للحالة.
    - إنشاء طابور محلي اختياري لإحصاءات Usage Statistics بعد تحديد payload والموافقة وBackend.
    - عدم رفع Medication names أو Strength أو notes أو أي نص صحي.
    - عدم جعل الرفع شرطًا لعمل Alarm أو تسجيل Dose.

11. **التحقق والاختبارات النهائية**
    - تشغيل `flutter test` و`dart format .` و`flutter analyze`.
    - اختبار الواجهة على أحجام Android مختلفة.
    - تنفيذ اختبار جهاز حقيقي لمصفوفة: قفل الشاشة، إعادة التشغيل، التطبيق المغلق، Battery Saver، رفض الصلاحيات، Alarm متكرر، Snooze عبر منتصف الليل، وتغير الوقت.
    - تسجيل نتائج اختبار الجهاز في `docs/AI_LOG.md`.

## مخاطر موثوقية التذكير

- قيود Android ومصنّع الجهاز قد تمنع exact Alarm أو إضاءة الشاشة رغم صحة منطق Dart.
- إعادة تشغيل الهاتف وتغير الوقت والمنطقة الزمنية قد ينتجان Alarms قديمة أو مكررة إن لم تتم إعادة الجدولة.
- Battery Saver قد يقيّد الخلفية؛ لا يمكن اعتبار المتطلب محققًا دون اختبار أجهزة حقيقية متعددة.
- لا يجوز إضافة plugin أو permission قبل التحقق من API والإصدار الموجودين في `pubspec.lock` ووثائق Android الحالية.
